Case 01 · AI + deterministic

The filing agent that knows when not to file

Context
Property-management back office, shared inbox
Status
In production
My role
Co-built; led production hardening, scope alignment and the review layer
Stack
n8n · Claude API (Haiku) · Gmail · cloud document storage · Notion

The problem

A busy shared inbox receives a steady stream of attachments: invoices, estimates, inspection reports, association notices, owner and tenant documents. Each one had to be opened, identified, renamed according to an internal SOP and dropped into the right subfolder of the right property, by hand.

Why a simple automation wasn't enough

A mail rule can match a sender. It can't read a PDF and notice that the property address sits in the document header, not in the email. It can't tell a legal notice to a tenant from an inspection report that happens to be titled "Notice". And the property folders are named slightly differently from how vendors write addresses ("Dr South" vs. "Dr S"). The job needs reading, and reading needs AI. But filing into the wrong folder is worse than not filing at all, so AI couldn't be the last word.

AI decides

  • What kind of document this is (~15 types)
  • Is it noise?
  • Extracts address, vendor, work order, dates
  • How confident it is about the type only

Code decides

  • Which folder it goes to (verified against the real tree)
  • The filename, per SOP
  • Whether this type is in scope
  • Overrides when signals are unambiguous

People decide

  • Low-confidence documents
  • Addresses with no matching property
  • Which document types get automated at all
  • Anything the agent refuses to guess

What broke in production, and what changed

FailureFix
Two attachments in one email produced the same filename, so one overwrote the otherUnique identifier per document, a collision suffix, and a separate error log
The model kept lowering confidence on inspection reports over address doubts, despite instructions. In-scope reports stopped being filedA deterministic rule: when sender and filename pattern are unambiguous, the type is not a matter of opinion. Confidence floor applied, address parsed from the filename

Results

Live on real mail since its first week. In a first-day audit of 35 documents, every classification reviewed was correct. In its first two weeks it logged hundreds of attachments, filed the approved types automatically, and sent the uncertain ones to a review queue with a plain-language reason.

Still open, stated plainly: the “retain” path Awaiting a real case and the hand-off to the accounting system Built, not connected.

Model choice

A larger model was tested and was both less precise on this task and more expensive. The smaller, faster model stayed. Bigger isn't automatically better for narrow classification with a tight schema.

AI confidence measures how sure the model feels, not whether it's right. The architecture has to check.

Case 02 · Deterministic by design

When rules beat a model: the vendor report pipeline

Context
Recurring vendor service reports for hundreds of properties
Status
In production
My role
Designed and built end to end
Stack
n8n · JavaScript · Gmail · storage REST API · PDF rendering API

The problem

Service vendors send visit reports by email, sometimes as an attachment, sometimes as the email body itself. Someone on the team printed body-only emails to PDF, renamed them and filed them under the property.

The decision: no LLM

The signals here are strong and stable: known senders, recurring subject words, predictable attachment names. So instead of a model, the pipeline scores signals (sender +2, attachment name +2, subject +1, body +1) and accepts at a conservative threshold. Cheaper, instant, fully explainable, and editable by anyone who can read a list of keywords.

FailureFix
Reports landed in a vendor folder instead of the propertyFolder search restricted to descendants of the correct parent
The same email processed on every pollMark as read immediately after classification
Two reports arriving in the same hourly batch got each other's folderPer-item resolution that always references that item's own source data
A fix worked in the editor but never ran in productionIt was saved, not published. Publishing is now part of the change checklist
Paid PDF service: adopt or not?Measured credit use per PDF on the free tier first, then decided

The best AI decision is sometimes not using AI. Use the model where reading is hard, not where matching is easy.

Case 03 · Human-in-the-loop

An undo button for automation: approval-gated corrections and a review hub

Context
Documents already filed in the wrong place
Status
Built, run on demand Review hub live
My role
Designed and built both
Stack
n8n · data tables · storage REST API · Notion

The problem

After a one-day bug and a scope change, some documents sat in the wrong subfolder. Fixing them by hand meant asking the client team for time, and giving the builder write access to their storage UI wasn't the right answer either.

The approach

A second workflow that proposes, waits, and only then acts. It reads what the filing agent logged, checks where each file really is today, and writes a proposal: move from here to there, already in place, or can't resolve and why. Nothing moves until a person marks the row approved. Errors come back as data, never as a crashed run.

The review hub

The client team needed to see what the agents did without asking the developer. A small Notion space holds four plain-language pages (filing criteria, what the agent does, what to do if something looks wrong, who owns which access) and two live databases the agents write to: a review queue and a corrections log.

Internal log states are translated before they reach people. "Revisar: propiedad no encontrada" becomes “The address does not match any property folder.” A reviewer should read a decision, not a status code.

Human review isn't where automation failed. It's the part of the design that lets the rest run unattended.

Case 04 · Discovery & feasibility

Reading the API before quoting: a utility-bill entry agent

Context
Monthly utility statements entered into property-management software
Status
Designed
My role
Process mapping, scope, technical feasibility
Stack (planned)
n8n · LLM extraction · spreadsheet lookup · PM software

The process, mapped in 8 steps

Detect the statement email → extract account, dates and each charge type → look up how that property recharges tenants in a billing tracker → enter one charge through a utility-bill module with the right ledger accounts → create the other bill by copying last month's and updating totals, dates and lines → replace the PDF → update the tracker and label the email → send anything ambiguous to review.

The finding that changed the plan

The software's reporting API is read-only. It can list properties and ledger accounts, but it can't create a bill or attach a document. Writing requires a different channel (an email-in bill feature, admin-level credentials) and possibly a native automation feature the account already had.

The decision

No proposal or estimate goes out until what can and can't be automated is settled. When it does, it offers two paths: faster with more risk, or slower with less margin for error.

"Can it connect?" is the wrong question. Ask "can it write?" before promising automation.
